Jenkins is designed from the ground up to be extensible.
Most functionality in Jenkins—from source code management and build tools to user interface enhancements and notification systems—is implemented as plugins.

== How Plugins Work

Jenkins defines numerous *extension points* (interfaces or abstract classes) that model aspects of its behavior.
Plugins implement these extension points and mark their implementations with `@Extension`.
During startup, Jenkins scans plugin JARs (or HPI/JPI packages), discovers these implementations, and registers them into the active runtime.

=== Class Loading and Isolation

Jenkins loads each plugin in its own class loader (`PluginClassLoader`) to prevent dependency conflicts between plugins and Jenkins core.
Plugins can declare dependencies on other plugins, and Jenkins arranges the class loaders so that classes exported by dependencies are accessible while keeping unexported internals isolated.

=== Seamless Integration

Plugins participate across all major Jenkins subsystems just like built-in classes:

* *Persistence:* Plugin data is persisted using XStream, saving XML files in `JENKINS_HOME` and maintaining backward compatibility across versions.
* *Web Views:* Plugins provide UI views using Jelly or Groovy that render seamlessly within the Jenkins UI layout.
* *HTTP Routing:* Plugins can bind methods and objects to URLs via Stapler to expose REST endpoints or web pages.
* *Static Assets:* Plugins can serve static resources such as icons, images, JavaScript, and CSS.
