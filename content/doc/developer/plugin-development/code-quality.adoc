Jenkins plugins use automated checks to catch defects and compatibility problems early.
The checks available to a project depend on its build configuration and languages.
This page summarizes the Java and Groovy guidance for Maven-based plugins and links to the detailed procedures.

== Start with the plugin parent POM

Most Maven-based plugins use the link:https://github.com/jenkinsci/plugin-pom[Jenkins plugin parent POM].
It provides a shared build configuration, including static analysis and tests.
Keep it reasonably current so the plugin can benefit from improvements to those tools.
See link:build-process/[Plugin Build Process] and the link:/doc/developer/tutorial-improve/update-parent-pom/[parent POM update tutorial].

Run the checks configured for the plugin as part of its normal build:

[source,shell]
----
mvn clean verify
----

Review the output and address findings that apply to the code.
When a SpotBugs finding is a false positive or cannot reasonably be fixed, document the reason in a narrowly scoped suppression.
The link:/doc/developer/tutorial-improve/add-more-spotbugs-checks/[SpotBugs tutorial] explains how to enable deeper analysis, review findings, and maintain exclusions.

== Make nullability explicit

Annotate API parameters and return values when null is allowed or prohibited so callers and static analysis tools can reason about the contract.
For Jenkins plugin code, use the SpotBugs annotations supplied by the plugin parent POM rather than the dormant JSR-305 annotations.
See the link:/doc/developer/tutorial-improve/replace-jsr-305-annotations/[annotation migration guide] and the examples in link:pipeline-integration/[Pipeline Integration].

== Check Jenkins-specific security concerns

General static analysis does not cover every security pattern used by Jenkins.
The Jenkins Security Scan uses Jenkins-specific CodeQL queries to detect vulnerabilities common in plugins.
See the link:/doc/developer/security/scan/[Jenkins Security Scan guide] for enabling it in a GitHub repository and interpreting its results.

== JavaScript and other languages

For JavaScript in a Maven-based plugin, the plugin parent POM can run npm or Yarn and report ESLint results to Jenkins.
See its link:https://github.com/jenkinsci/plugin-pom#npm-or-yarn[npm or Yarn setup] and
link:https://github.com/jenkinsci/plugin-pom#configuring-eslint-to-report-results-to-jenkins[ESLint reporting instructions].
These instructions configure reporting; each plugin still defines which ESLint rules and source files to check.

For TypeScript and other languages, use the linting, tests, and security checks configured by the project.
The Jenkins plugin parent POM does not define a shared configuration for those languages.
