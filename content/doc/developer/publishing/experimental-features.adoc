---
title: Delivering Experimental and Preview Features
layout: developer
---

Jenkins developers can use several mechanisms to test changes with users or downstream components before a general release.
Choose a mechanism based on what is being previewed: a component build, a plugin release, an opt-in behavior, or a Java API.

== Testing changes across components

Use link:/doc/developer/plugin-development/incrementals/[Incrementals] when a change in Jenkins core or an upstream plugin needs to be tested by a downstream component before release.
Incremental builds let a downstream project consume and test an unreleased upstream version through the normal Maven workflow.
The Incrementals guide explains how to produce and consume these builds.

== Offering experimental plugin releases

The link:/doc/developer/publishing/releasing-experimental-updates/[experimental update center] can distribute alpha and beta plugin versions to users who opt in.
That update center is deprecated in favor of Incrementals, so use Incrementals for new testing workflows.
The experimental update center serves only the latest version of each plugin and that version may be incompatible with a user's Jenkins version.
See the guide for its existing configuration and release instructions.

== Making behavior opt in

For a Jenkins core feature that needs an administrator-controlled opt-in during development, a system property can gate the behavior.
The link:https://javadoc.jenkins.io/jenkins/util/SystemProperties.html[`SystemProperties` API] centralizes reads of Jenkins application-level properties and also supports servlet context initialization parameters.
This is a configuration mechanism, not a feature distribution or user-interface toggle.
Document the property name, default behavior, how to enable it, and whether a restart is required.

== Exposing a provisional Java API

When a Jenkins Java API is available for early use but its design may still change, Jenkins core can mark it with `@Restricted(Beta.class)`.
This signals that the API is not yet stable and allows its implementation or signature to change before it becomes a supported compatibility commitment.
See the blog post link:/blog/2018/04/30/using-the-beta-annotation/[Using new core APIs with the Beta annotation] for background and usage details.

== Describing a project preview

The link:https://github.com/jenkinsci/jep/blob/master/jep/14/README.adoc[Jenkins Roadmap JEP] uses *Preview* for work made available to users or contributors for feedback.
It describes preview as a status that can be delivered in different ways, including an opt-in feature, a beta API, an experimental update, or another documented mechanism.
Use the roadmap to communicate project status; choose one of the mechanisms above to deliver the code.
