As organizations scale their CI/CD infrastructure, managing local user accounts directly inside Jenkins quickly becomes an administrative bottleneck and a security risk.
Centralizing identity management ensures that when team members join, change roles, or leave, their permissions update automatically across your entire toolchain.

This November, we are highlighting the **Microsoft Entra ID (previously Azure AD) Plugin**—a community-maintained integration that brings enterprise Single Sign-On (SSO), granular group-based authorization, and **Azure Workload Identity** support directly to your Jenkins controller.

== What is the Microsoft Entra ID Plugin?

This plugin connects your Jenkins instance to **Microsoft Entra ID** as a Security Realm and integrates with Jenkins authorization strategies.
Instead of maintaining separate credentials for Jenkins, developers authenticate using their existing Microsoft corporate accounts, inheriting your organization's Multi-Factor Authentication (MFA) and conditional access policies.

== Key Features & Latest Highlights

=== 1. Latest Highlight: Secretless Azure Workload Identity (Federated Credentials)
Managing, rotating, and storing static client secrets or certificates is one of the biggest operational headaches in cloud security.
One of the latest additions to the plugin is native support for **Workload Identity (Federated Credentials)** on Azure.

Federated credentials let the plugin exchange an OIDC-issued JWT for an Entra ID access token.
The plugin supports supplying this token either through:

* **Federated Token File:** Reading a JWT from a file path specified by the `AZURE_FEDERATED_TOKEN_FILE` environment variable (ideal for Kubernetes workloads).
* **OpenID Connect Provider Plugin:** Referencing a Jenkins OpenID Connect ID token credential directly.

=== 2. Traditional Credential Options Still Supported
For environments not yet migrated to OIDC federation, the plugin continues to support both **Client Secrets** and **Client Certificate authentication** (using a PEM-encoded private key).

=== 3. Smart User and Group Autocomplete
Configuring permissions via raw Object IDs is tedious and error-prone.
Using the Microsoft Graph API, the plugin lets administrators search for users and security groups by display name when assigning permissions.
The **Role Strategy plugin** natively autocompletes Entra ID users and groups in its **Add user** and **Add group** dialogs through the Authentication and Authorization Commons plugin.
Autocomplete is also available in **Entra ID Matrix-based security**.
The Jenkins community continues to actively develop the plugin and its integrations with authorization strategies.
Ongoing work aims to bring Entra ID autocomplete to standard Matrix Authorization and, once equivalent functionality is available, deprecate the plugin's Entra ID-specific matrix strategy.

=== 4. Broad Authorization & JCasC Compatibility
The plugin integrates with popular authorization strategies (such as Matrix-based, Role-based, and Folder-based Authorization) and supports **Jenkins Configuration as Code (JCasC)** so you can version-control your security realm and permission mappings.

== Getting Started with Workload Identity

Setting up Microsoft Entra ID federated credentials takes just a few steps across Azure and Jenkins:

1. **Register an App in Entra ID:** In the Microsoft Entra admin center, create a new **App registration**.
   Add a Redirect URI pointing to `https://jenkins.example.com/securityRealm/finishLogin` and enable **ID tokens** under **Authentication**.
2. **Add a Federated Credential:** Inside your App Registration, navigate to **Certificates & secrets** -> **Federated credentials** -> **Add credential**, and configure the **Issuer**, **Subject**, and **Audience** to match the JWTs issued by your OIDC provider.
3. **Grant Microsoft Graph Permissions:** Add the delegated permissions `openid`, `profile`, and `email`, plus the application permissions `User.ReadBasic.All`, `GroupMember.Read.All`, and `Group.Read.All`.
   Remove `offline_access` and `User.Read` if they are listed, then grant tenant-wide admin consent.
4. **Configure Jenkins Security:** Install the `azure-ad` plugin via **Manage Jenkins** -> **Plugins**.
   Navigate to **Manage Jenkins** -> **Security**, select **Entra ID** as your Security Realm, enter your **Client ID** and **Tenant**, and set **Authentication Type** to **Workload Identity (Federated Credentials)**.
   Provide a valid JWT through `AZURE_FEDERATED_TOKEN_FILE`, or configure the Federated Credentials field with an `OpenID Connect id token` credential.
5. **Assign Permissions:** Select an authorization strategy such as **Matrix-based security**, grant your admin user or group permissions using its Object ID so you do not lock yourself out, and save your configuration.
